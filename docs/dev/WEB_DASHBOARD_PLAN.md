# Web ダッシュボード（ブラウザで状態確認）計画

## 概要

main.py とは独立して起動できる Web ダッシュボードを追加し、既存の Textual ダッシュボードと同等の状態（概要・ログ・タスク・Intent・設定）をブラウザで参照できるようにする。

---

## 1. 要件整理

### 1.1 機能要件（現行ダッシュボードと同等）

| 画面       | 表示内容                                              | データソース（現行）                                                               |
| ---------- | ----------------------------------------------------- | ---------------------------------------------------------------------------------- |
| **概要**   | プロジェクト目標、イテレーション/継続判定、タスク統計 | StateManager.get_status(), config.AGENT_CONFIG, StateManager.get_task_statistics() |
| **ログ**   | 実行ログのリアルタイム表示（日付別ファイル）          | config.LOG_DIR（コンテナ内は /workspace/logs）/execution_YYYYMMDD.log              |
| **タスク** | タスク一覧、選択時の詳細・結果・エラー                | StateManager.get_all_tasks_from_files(), get_task_by_id()                          |
| **Intent** | 変更意図一覧、詳細、Diff 表示                         | IntentManager, ADRManager, GitHelper                                               |
| **設定**   | プロジェクト/LLM/メインループ設定、環境情報           | config                                                                             |

### 1.2 非機能要件

- **main.py と独立**: エージェントを起動せずに Web サーバー単体で起動し、永続化済みの state/log を参照できる。
- **読み取り専用**: 状態の変更・タスク操作は行わない（表示のみ）。
- **同一データソース**: state/log のパスは config（コンテナ内は /workspace/state, /workspace/logs に固定）等、既存と同一。

---

## 2. 技術選定

- **バックエンド**: FastAPI（SSE 対応、軽量）
- **フロント**: サーバー描画 + 軽量 JS。更新は **ポーリング** またはログのみ SSE。
- **データ層**: 既存 StateManager / IntentManager / ADRManager / GitHelper / config をそのまま利用。

---

## 3. ポーリングと Stateful UI の扱い（UX）

### 3.1 問題

ポーリングでデータを再取得し、表示を更新する際に **UI 上の Stateful な状態がリセットされる** 可能性がある。これは UX に直結する。

- **選択状態の喪失**: タスク一覧で「どのタスクを選択していたか」、Intent 一覧で「どの Intent を選択していたか」が、更新のたびにクリアされる。
- **タブ状態の喪失**: 能動タブ（概要/ログ/タスク/Intent/設定）が、フルリロードや再描画で「概要」に戻ってしまう。
- **スクロール位置の喪失**: ログや長いリストでスクロールしていた位置が、更新で先頭に戻る。
- **詳細ペインの flicker**: 一覧と詳細を左右に表示している場合、一覧の再描画で詳細が一瞬消える、または別タスクの詳細に切り替わる。

これらを放置すると「更新のたびに操作がやり直しになる」ため、**設計段階で対策を組み込む**。

### 3.2 設計方針

- **クライアント側で UI 状態を保持**し、ポーリングで取得したデータで **中身だけ差し替え、選択・タブ・スクロールは維持する**。
- 更新は **可能な範囲で部分更新**（リストの行だけ更新し、選択行やスクロールは触らない）を優先する。

### 3.3 具体的な対策

| 状態                 | 対策                                                                                                                                                                                                                           |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **能動タブ**         | URL hash（`#tasks`, `#intents` 等）または JS 変数で保持。初回描画・ポーリング後の再描画時も、現在のタブを復元して表示する。                                                                                                    |
| **タスクの選択 ID**  | 選択中の `task_id` を JS で保持。API からタスク一覧を再取得してテーブルを更新する際も、同じ `task_id` の行を選択状態にし、詳細ペインはその ID で再取得して表示する。                                                           |
| **Intent の選択 ID** | 同様に `task_id`（Intent のキー）を保持し、一覧更新後も選択と詳細を復元する。                                                                                                                                                  |
| **スクロール位置**   | ログ・長リストでは、更新前に `scrollTop` を保存し、DOM 更新後に復元する。または「末尾に追従」モードの場合は常に末尾にスクロールするなど、更新と整合するルールを決める。                                                        |
| **一覧の再描画**     | 一覧を「全置換」せず、**差分だけ更新**（行の追加・削除・ステータス変更のみ反映）する実装にすると、選択行がずれにくい。実装コストと相談して、まずは「選択 ID を保持して再描画後に復元」で対応し、必要なら diff 更新を検討する。 |

### 3.4 実装上のルール

1. **ポーリングで取得するのはデータのみ**。タブ・選択 ID・スクロール位置はサーバーに送らず、クライアントの JS で保持する。
2. **再描画のタイミング**で、保持している「能動タブ」「選択 ID」を参照し、描画結果に反映する（タブの切り替え、該当行のハイライト、詳細ペインの内容取得）。
3. **ログタブ**は、末尾追従の場合は更新後に `scrollTop = scrollHeight` で末尾へ。ユーザーが手動で上にスクロールしている場合は、`scrollTop` を保存・復元するか、末尾追従を一時停止するなどの挙動を決める。
4. 新規実装時は、**「ポーリングで 5 秒ごとに更新」したときに、タブ・選択・スクロールが維持されるか**をチェックリストにして確認する。

## 4. 設計（API・画面・Docker）

- **API**: `GET /api/overview`, `/api/tasks`, `/api/tasks/{id}`, `/api/intents`, `/api/intents/{task_id}`, `/api/logs`, `/api/settings`。ログは必要に応じて `GET /api/logs/stream`（SSE）。
- **画面**: 1 ページでタブ切替（概要/ログ/タスク/Intent/設定）。各タブの内容は API で取得し、JS で描画。ポーリングは「能動タブに応じて必要な API だけ叩く」でも可。
- **Docker**: Web のみ起動するオプション、または既存 agent と同一コンテナで Web を別プロセスで起動するオプションを用意する。

---

## 5. 実装 Phase（Stateful UI を組み込み済み）

1. **Phase 1**: FastAPI 骨格、config（STATE_DIR/LOG_DIR は廃止済み。コンテナ内は /workspace/state, /workspace/logs 固定）読み込み、`/api/overview`, `/api/settings`。JSON 確認。
2. **Phase 2**: `/api/tasks`, `/api/tasks/{id}` と、概要・設定・タスクの HTML（タブ切替 + fetch）。**ここで「タブ状態」「タスク選択 ID」をクライアントで保持し、ポーリング後も復元する**ことを実装し、UX を確認。
3. **Phase 3**: ログ API とログタブ。**スクロール位置または末尾追従のルールを決め、更新後も維持する**。
4. **Phase 4**: Intent 一覧・詳細 API と Intent タブ。**Intent 選択 ID の保持と復元**をタスクと同様に実装。
5. **Phase 5**: ポーリング間隔の調整、Docker 起動オプション、ドキュメント整備。**「ポーリング時の Stateful UI 維持」を README または開発者向けドキュメントに明記**する。

---

## 6. まとめ

- ポーリング採用時は **「更新で選択・タブ・スクロールがリセットされない」** ことを UX 要件に含め、設計・実装・確認の各段階で組み込む。
- 対策の中心は **クライアント側での状態保持** と **再描画後の復元**。必要に応じて一覧の差分更新も検討する。
